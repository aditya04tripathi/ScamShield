# Software Requirements Specification (SRS) - ScamShield

## 1. Introduction

### 1.1 Purpose

The purpose of this document is to define the functional and non-functional requirements for ScamShield, a multi-modal scam detection platform designed to protect users from various forms of fraudulent activities across different digital communication channels.

### 1.2 Scope

ScamShield provides an integrated system for analyzing emails, URLs, audio files, and prompts for potential scam indicators. It leverages specialized machine learning models and local LLM orchestration to provide categorized risk scores and actionable remediation steps.

## 2. Overall Description

### 2.1 System Context

ScamShield consists of a FastAPI backend orchestration layer, a Next.js frontend user interface, and several external/local AI services including Hugging Face models and Ollama.

### 2.2 User Types

- **Standard User**: Can run scans on various modalities and view history.
- **Admin**: Can view system-wide stats and manage user reports.

### 2.3 Operating Environment

- **Platform**: Cross-platform (Linux/macOS recommended); frontend deploys on Railway.
- **Models**: Local execution using Ollama (Qwen 2.5) and Hugging Face Transformers.
- **Database**: MongoDB for scan history and user data.
- **Cache**: Redis for task state and results.

## 3. Functional Requirements

### 3.1 Modality Analysis

1. **Email Analysis**: The system shall classify emails for phishing using DistilBERT transformers combined with heuristic checks (urgency, credential harvesting).
2. **URL Analysis**: The system shall analyze URLs using BERT models and heuristic weights (IP detection, length, character entropy).
3. **Audio Analysis**: The system shall analyze audio files for deepfake artifacts using Librosa spectral analysis (MFCC, pitch variance, timbre anomalies).
4. **Prompt Injection**: The system shall detect jailbreak and prompt injection attempts using DeBERTa v3 models.
5. **UI-Based Scans**: The system shall support free-form text scans for general scam detection.

### 3.2 Result Generation

1. **Risk Scoring**: The system shall generate a risk score (0-100) for every scan.
2. **Signal Identification**: The system shall extract specific "signals" (e.g., "Urgent Tone", "Hidden Link") explaining the risk.
3. **LLM Explanation**: The system shall use a local LLM (via Ollama) to generate a human-readable explanation and remediation steps.

### 3.3 Data Persistence

1. **Scan History**: The system shall store scan results mapped to user sessions.
2. **Asynchronous Tasks**: Large scans (audio/files) shall be processed asynchronously using a worker/queue model.

## 4. Non-Functional Requirements

### 4.1 Performance

- **Latency**: Text/URL scans shall return results within 2 seconds.
- **Concurrency**: The system shall support multiple simultaneous scan requests.

### 4.2 Security

- **Data Integrity**: User scan data must be protected and isolated.
- **Input Validation**: All API inputs shall be validated to prevent injection or malicious payloads.

### 4.3 Reliability

- **Graceful Degradation**: The system shall remain functional even if individual ML models fail, providing metadata-based fallbacks.

## 5. System Constraints

- **Language**: Python 3.11+ (Backend), TypeScript/Next.js (Frontend).
- **Inference**: Must support local inference to ensure user privacy.
- **Deployment**: Frontend must be deployable on Railway; backend runs as a local or separately hosted FastAPI service.

## 6. External Interface Requirements

- **API**: RESTful endpoints provided by FastAPI.
- **UI**: Responsive web interface built with shadcn/ui and Tailwind CSS.
- **Storage**: MongoDB for persistent data, Redis for transient state.

## 7. Assumptions and Dependencies

- Users have Bun (frontend) and Python 3.11+ (backend) installed.
- System has sufficient memory (8GB+) to run machine learning models and Ollama.

## 8. Acceptance Criteria

- Successful detection of classic phishing emails with >90% accuracy in test sets.
- Identification of spectral artifacts in deepfake audio clips.
- Validated remediation steps generated by the LLM for high-risk scans.
